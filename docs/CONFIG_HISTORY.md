# 配置版本、回滚与操作日志

超级管理员进入「运营配置 → 配置版本与回滚」，按运费、优惠券、首页运营位或隐私政策筛选，分页查看版本、操作者、时间与完整快照。首次保存前保留原配置为初始快照，后续保存和回滚都生成新版本。首次变更之前没有可回滚的历史；不能恢复未被记录的更早配置。

在历史快照中选择「回滚至此版本」，填写原因后确认。回滚即生效，生成新的当前版本并写入操作日志；原有版本继续保留。四个配置表单重新加载，未保存的草稿会清除，确认框会提前说明。历史首页引用的商品或文章已下架、政策内容不符合当前发布规则等情况会拒绝回滚。其他管理员已更新配置时，旧页面回滚会被拒绝，需重新核对最新版本并确认。

侧栏「操作日志」支持按操作标识、用户名、目标 ID、起止日期筛选，分页及查看详情。用户名、目标 ID 支持包含查询，操作标识精确匹配；日期按北京时间，截止日期包含当天。显示已有后台业务日志与新配置保存/回滚日志，详情中的密码、令牌和密钥字段会遮盖。查看历史、回滚及日志读取均由服务端检查超级管理员权限。

## 上线步骤

1. 在部署新版后端之前，执行 `backend/schema.sql` 的 `CREATE TABLE IF NOT EXISTS config_versions` 语句；语句可重复执行，不覆盖当前配置及历史日志。
2. 部署新版 Go 服务与后台。四类配置通过统一事务保存，配置更新、版本和审计日志一起提交；数据库写入失败时不会部分生效。
3. 在验收环境验证下述流程。演示模式不访问生产数据库，四类配置、历史与日志只保存在当前标签页的会话存储，刷新后保留，关闭该会话后重置；小程序演示配置仍独立。

## 验收

- 分别修改并保存四类配置。首次保存产生初始快照 v1 和保存版本 v2，原配置内容完整保留，其他类型不受影响；再次保存版本递增。
- 查看初始快照，取消回滚时配置与历史均不变化；填写原因确认后恢复内容并生成 v3。表单和已保存预览重新读取，操作日志包含操作者、来源版本和原因。
- 两个管理员打开相同历史，一个先保存，再让另一个回滚。第二次操作必须提示配置已变化，当前内容、历史和日志不得产生失败操作的变更。
- 首页历史引用的商品下架后尝试回滚，应拒绝。无效配置、空原因、其他配置的版本 ID 均拒绝；版本、日志或配置写入失败时整笔事务回滚。
- 运营人员尝试直接调用三个新接口，应拒绝；无效/停用/过期会话不能读取日志。密码和令牌不出现在日志详情。
- 按操作类型、操作者、目标及日期组合筛选，核对总数和分页；北京时间当天 23:59 的日志包含在截止日内，次日 00:00 排除。空结果、加载失败重试和快速切换筛选正常。

本地验证：`npm run test:config-history`、`npm run check`、`npm run test:flows`，以及在 `backend/` 执行 `go test ./...` 和 `go vet ./...`。真实 MySQL 锁竞争及迁移须在验收数据库验证。
