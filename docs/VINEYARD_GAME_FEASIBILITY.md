更新：独立微信小游戏第一版已实现，采用原生 Canvas 2D 及现有 Go / MySQL。当前实际范围、运行方法和验收边界见 [首版实现说明](VINEYARD_GAME_IMPLEMENTATION.md)；下文保留立项时的长期选型与规划。

后续方向已更新为第三人称下地操作、内置可选人物，以及沿葡萄成长推进的关卡和天气/市场事件。最新规划见 [第三人称体验与闯关设计](VINEYARD_GAME_IMMERSION_DESIGN.md)。

调研日期：2026-10-12。业务方向：鲜食葡萄种植与销售。用户已确定：由葡萄园小程序跳转到独立微信小游戏，游戏使用独立 AppID 和游戏工程。依据：当前项目代码、微信官方类型定义、游戏引擎官方文档、农业推广与研究资料。

## 1. 结论与推荐路线

技术上可实现，而且现有后端、数据库、运营后台和种植课堂可以复用。建议定位为“基于真实农事因果关系的 2D 鲜食葡萄经营游戏”：玩家管理水肥、枝叶与果实负载，决定何时采收，再通过分级、保鲜和销售获得利润。

核心采用可解释规则与简化数值模型；画面采用 2D 葡萄园地图；服务器保存正式进度并结算结果。首版重点验证完整的一季经营闭环。

正式路线已经确定：葡萄园小程序增加“我的葡萄园”等跳转入口，游戏作为独立微信小游戏运行。推荐 Cocos Creator 2D + TypeScript，服务端复用当前 Go 云托管和 MySQL，并保留独立的游戏存档、虚拟库存和账本。

小游戏拥有自己的 AppID、微信登录、资源包、体验版和发布流程。小程序端只需增加入口及必要的跨应用衔接。后续返回课堂或商城属于可选业务联动，游戏经营闭环可以独立完成。

Cocos 官方微信构建目标是小游戏，产物包含 game.json 并使用小游戏 AppID，不能直接当作现有普通小程序中的一个页面。[Cocos Creator 3.8 微信小游戏发布说明](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/publish-wechatgame.html)

本次未能读取微信当前运营规范及游戏类目资质页的官方正文，不能判断具体账号的最终审核结果。实施前应在小游戏后台或官方工单确认主体、具体游戏类别及发布资质。涉及网络游戏出版的适用要求，可查国家新闻出版署公布的审批事项；不以“无内购”推断免除相关要求。[国家新闻出版署：出版国产网络游戏作品审批](https://www.nppa.gov.cn/bsfw/xksx/cbfxl/wlcbfwspsx/202210/t20221013_600725.html)

云托管官方支持小程序通过 wx.cloud.callContainer 访问关联环境中的服务。同主体的跨应用环境访问涉及环境共享配置，不能假设新小游戏直接继承原小程序的访问权限。小游戏首版优先评估 HTTPS 请求同一 Go 服务；若采用小游戏云开发访问方式，应额外验证其 SDK、环境权限和身份传递。[CloudBase：小程序访问云托管](https://docs.cloudbase.net/run/develop/access/mini)

两个需要提前处理的代码约束：

- 当前小程序账号请求使用连接级 MySQL GET_LOCK，业务处理可能另取数据库连接；连接池上限是 20 个。游戏应在进入、恢复和操作时同步，避免秒级心跳。长离线补算必须限制事务耗时，实施前压测与商城并发时的连接等待。
- 当前登录换码只使用一组 WECHAT_APP_ID / WECHAT_APP_SECRET，并以小程序 OpenID 为会话主体。独立小游戏必须扩展登录及身份映射，不可直接用原接口来交换另一 AppID 的登录 code。
- 首页运营位的跳转目标具有前后端白名单。若入口由运营后台控制，需要同步增加小游戏目标类型、目标 AppID 校验和小程序跳转处理。

## 3. 玩法怎样体现真实种植经验

### 3.1 一季经营闭环

接手已成园地块 → 冬剪与生产计划 → 萌芽与枝叶管理 → 开花坐果与负载调整 → 膨大期水肥管理 → 成熟期品质与天气权衡 → 采收 → 分级包装与保鲜 → 销售与利润结算 → 采后恢复和下一季。

从成园开始可以让首季覆盖实际生产决策。葡萄属于多年生果树，果实出现在当季新梢上；冬剪保留的芽和当季负载会影响成熟与树势，因此不应每次收获后重置成一块空地。新建园和幼树培养可作为后续玩法。[OSU：Growing table grapes](https://extension.oregonstate.edu/catalog/ec-1639-growing-table-grapes)

### 3.2 玩家操作与系统反馈

以下是依据农艺关系提出的游戏设计，具体曲线和数值需由当地种植人员校准。

| 决策 | 游戏内部影响 | 玩家可以看到的反馈 |
| --- | --- | --- |
| 冬剪与留芽 | 潜在新梢、果穗数量和后续负载 | 本季预计产量范围、树势压力 |
| 灌溉 | 根区水量、缺水压力、用水成本及供水波动 | 土壤状态、缺水提示、累计用水 |
| 按诊断施肥 | 简化养分供需、树势与成本 | 营养不足或过旺提示；施肥收益有上限 |
| 疏梢、整枝和适度摘叶 | 通风、光照、有效叶量与暴露风险 | 冠层疏密、成熟效率、病害或日灼风险变化 |
| 疏穗、疏粒 | 果实数量与单粒增长资源分配 | 总产量、粒重和成熟进度的权衡 |
| 巡园与防护 | 发现风险、选择管理措施并支付工时或材料成本 | 风险变化与已造成的损伤分别展示 |
| 采收 | 锁定该批次成熟度与初始商品质量 | 糖度或口感成熟度、粒重、外观、商品率 |
| 分级、保鲜与销售 | 库存损耗、销售速度、售价和渠道成本 | 各等级售出量、报损量、收入与利润 |

鲜食品质不宜只用糖度表示。UC Davis 指南同时讨论成熟度、着色、硬度、裂果、腐烂和日灼等缺陷，且指出货架寿命与品种、温度管理及腐烂敏感性有关。其地区性采收数值不能直接套用于所有中国品种。[UC Davis：Grape 成熟品质与采后管理](https://postharvest.ucdavis.edu/produce-facts-sheets/grape)

设计中应保留几个条件关系：

- 品种决定目标外观，绿色品种成熟不等于变红。
- 留果量需要与树势、有效叶量和天气匹配；不能设成疏果越多总收益越高。
- 通风与适度光照有收益，过度暴露也会带来日灼等代价，效果与时机有关。[OSU：冠层管理与葡萄树平衡](https://extension.oregonstate.edu/catalog/em-9071-role-canopy-management-vine-balance)
- 避雨设施有建设、维护和光照通风代价。研究中的避雨设施减少了部分病害，但白粉病仍需管理，不能作为对全部病害的免疫升级。[鲜食葡萄避雨栽培原始研究](https://doi.org/10.1016/j.cropro.2014.10.024)

每次重要结算生成两三条原因说明，例如“保留果穗偏多，成熟推进放缓”“及时分级与保鲜，销售损耗减少”。提示内容可以直接关联现有种植课堂。

### 3.3 首版范围

建议首版限定为：

- 一个经真实园区人员确认的地区、一个主栽鲜食品种；参数结构支持以后增加品种。
- 4–12 个管理地块，以地块为模拟单元；同一地块中的大量葡萄株以平均状态表示。
- 一套棚架或栽培设施；滴灌、避雨或保鲜设施中选择少量可升级项。
- 6–8 类核心农事，1–2 类当地常见病害，普通年、干旱年和多雨年天气剧本。
- 采收分级、库存损耗、两类虚拟销售渠道、经营账本和季末复盘。
- 新手教学与课堂关联，保留下一季树势和设施。

自由行走、多人实时协作、用户间交易、复杂物理、3D、完整土壤化学和植物生长调节剂细节，会显著扩大首版范围，建议留到后续。

游戏中的销售采用独立虚拟账本。真实商城商品、支付订单和实际库存沿用现有业务系统，游戏收获不自动生成真实可发货商品。

## 4. 农艺模拟如何实现

### 4.1 三层模型

| 层 | 负责什么 | 实现形式 |
| --- | --- | --- |
| 物候层 | 休眠、萌芽、开花坐果、膨大、成熟、采收、采后恢复 | 状态机 + 当地季节条件 + 可配置温度累积 |
| 生长与损伤层 | 水分、简化养分、树势、冠层、负载、粒重、成熟和病害 | 每模拟日数值更新 + 有上下限的响应曲线 |
| 经营层 | 工时、耗材、设施、采收批次、品质分级、保鲜和销售 | 库存与账本规则 |

Go 端实现纯模拟函数，输入“上一状态、规则版本、天气、已执行动作和目标模拟时间”，输出“新状态、事件、库存与成本变化”。不在模拟函数中访问数据库、读取本机当前时间或调用外部 AI，方便回放和验证。

### 4.2 最小状态与参数

静态配置：地区、品种、地块面积或株数、土壤持水与排水能力、根深、设施、物候阈值、正常产量与粒重范围、外观目标、病害及裂果敏感性。

动态农艺状态：阶段、温度累积、根区可利用水、简化营养供需、树势或储备、冠层密度与有效叶量、穗数和粒数、平均粒重、糖度或成熟指标、外观成熟度、各类损伤。

经营状态：经营币、工时、耗材、设施耐久、采收批次、剩余库存、品质等级、销售和报损记录。

数值配置按“地区 × 品种 × 栽培方式”组织。没有实测依据的参数标为游戏简化假设，注明待校准，不填看似精确的全国通用阈值。

### 4.3 每日计算顺序

天气与阶段条件 → 物候推进 → 降雨、灌溉、蒸散与排水 → 水肥压力与有效叶量 → 生长、负载和成熟 → 裂果与病害损伤 → 树体储备 → 库存品质衰减和经营成本。

首版采用明确的模拟日边界：先结清已经结束的模拟日，农事作用于当前尚未结算日，资源立即扣减；同一天的动作按服务器确认顺序记录。采收与销售立即变更批次库存，采后日衰减从下一模拟日计起。服务器时间与模拟日的映射、取整及余量规则固定，不因同步次数改变。后续需要日内精细过程时，再扩展子日步进。

根区水分可使用经简化的每日水量平衡，各项统一为地块水深等一致单位：

~~~text
当日根区水量 = 昨日水量 + 有效降雨 + 有效灌溉
               - 蒸散消耗 - 排水损失
~~~

初版可以不模拟地下水毛管上升，但要标明假设，并根据土壤设置容量及排水过程。FAO 56 提供根区每日水量平衡及水分胁迫方法，可用作模型框架；首版仅实现所需部分，不宣称完整实现全部 FAO 模型。[FAO 56 第 8 章](https://www.fao.org/4/X0490E/x0490e0e.htm)

生长与成熟采用专家审核的响应曲线：适量供水与负载允许正常生长，缺水或过载限制增长；营养过旺、过度遮阴或过度暴露产生相应代价。

病害区分“感染或发生风险”“已经造成的叶片或果实损伤”。霜霉病与白粉病采用不同条件逻辑；如果只有每日天气资料，应实现简化风险等级，不能冒充需要逐时温度、叶湿等数据的完整田间预警模型。[UC IPM 霜霉病指南](https://ipm.ucanr.edu/agriculture/grape/downy-mildew/)、[UC IPM 白粉病指南](https://ipm.ucanr.edu/agriculture/grape/powdery-mildew/)

### 4.4 产量、品质和利润

下式为游戏核算关系，系数、等级和售价须另行校准：

~~~text
理论鲜重 = 穗数 × 平均每穗粒数 × 平均粒重
商品鲜重 = 理论鲜重 - 不合格果实重量
销售收入 = 各等级实际售出重量 × 对应渠道成交价
本季利润 = 销售收入 - 农资、人工、设施使用、包装、
           保鲜和渠道成本
~~~

损伤按批次或互斥分类分配，防止同一颗果同时因裂果和病害被重复扣重。采收生成批次，销售消耗批次库存；未售出的葡萄继续发生品质衰减和报损。

设施成本明确区分现金流和利润口径：购买设施当期扣现金；经营利润可按可配置使用年限分摊，避免同一成本在两处重复扣除。首版售价使用固定渠道规则和少量季节事件，暂不模拟真实市场交易撮合。

### 4.5 天气与游戏时间

首版使用经整理、授权可用的当地历史天气或专家审核剧本，保留连续热浪、连阴雨等时间相关性。只随机抽每天晴雨，会破坏实际天气过程。

一季压缩为约 14–21 个现实日是可测试的节奏假设，内部仍按模拟日计算；新手体验季可以更短。农事窗口根据模拟物候判断。首版不依赖实时天气接口，后续实况天气模式需要数据来源、许可、费用和失败降级方案。

离线托管、关键窗口保护、可补算上限由玩法规则统一定义，并清楚展示。不能默默丢掉超限时间，也不能让上线刷新频率改变同一段时间的生长结果。

### 4.6 真实经验如何转成规则

与种植人员整理代表性年度的物候、天气、水肥、修剪留芽、留穗、病害、采收、粒重、糖度、商品率和销售记录。

先校准正常物候与产量，再校准水分、负载和损伤，最后调整经营节奏与收益。数据足够时，保留一季未参与校准的记录做回放验证；数据不足时先用专家审核案例，明确模型的验证程度。

每条规则保留来源、适用地区与品种、原始单位、参数值、专家审核人和版本。验证“操作 → 状态 → 结果”的方向与时机，并测试是否出现重复浇水、极端疏果或无限施肥等单一获胜策略。

## 5. 客户端选型与画面实现

| 方案 | 对本项目的适配 | 主要投入 | 判断 |
| --- | --- | --- | --- |
| Cocos Creator 2D | 有官方微信小游戏构建目标，便于制作场景和动画 | 游戏工程、美术工作流、独立身份和跳转 | 本项目首选 |
| 手写小游戏 Canvas 2D | 可实现简单地块场景，需自己维护场景、交互和素材流程 | 地块绘制、命中检测、短动画、资源管理 | 极简原型可用，长期扩展投入较大 |
| PixiJS | 适合大量 2D 精灵，但需针对小游戏运行环境验证适配 | 图片、字体、事件、资源加载及版本兼容 | 已有团队经验时再考虑 |
| Phaser | 官方主要定位浏览器 HTML5 游戏框架 | 微信运行环境和加载、音频等适配 | 本项目首版不优先 |
| web-view + H5 | 适合复用已经存在的 H5 游戏 | 网页加载、桥接、业务域名 | 与已确定的独立微信小游戏路线不匹配 |

建议以 Cocos Creator 3.8 LTS 文档对应的稳定版本开展原型，验证后固定具体版本。PixiJS 官方支持自定义环境适配，但该能力不等同于微信小游戏开箱即用。Phaser 官方定位主要为浏览器 HTML5 游戏框架。[Cocos 微信发布文档](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/publish-wechatgame.html)、[PixiJS 环境文档](https://pixijs.com/8.x/guides/concepts/environments)、[Phaser 官方仓库](https://github.com/phaserjs/phaser)

建议使用俯视或轻等距 2D 地图。葡萄架、叶幕、果穗、设施和天气效果作为图层；物候变化切换素材，农事播放短动画。每株葡萄不需要独立生理模拟。

仓库、农事记录、经营面板和教学提示采用 Cocos UI。地图使用 Sprite、图集、简单摄像机拖动或缩放和短动画，不按渲染帧发送服务端请求。

资源使用 Cocos Asset Bundle 和当前支持的小游戏分包、远程资源加载方式。图片、图集和音频按版本管理，按场景加载并限制缓存。后台隐藏时暂停渲染和音效，恢复时同步存档；退出释放监听和音频实例，按目标终端与内存告警处理资源。

包体额度以当前小游戏账号规则和开发者工具上传检查为准。远程加载美术资源不等于远程执行脚本；规则配置只包含经过服务端校验的数据。

建议工程划分为三个可分别构建和发布的部分：现有小程序入口、新增 Cocos 游戏工程、现有 Go 服务中的游戏模块。Go 模拟内核与 Cocos 渲染分离；客户端共享数据契约和配置结构，不复制正式收益结算代码。

## 6. 服务端、存档与身份设计

### 6.1 推荐架构

~~~mermaid
flowchart LR
  MP["现有小程序：入口、商城、课堂"] --> ENTRY["游戏入口"]
  ENTRY --> CLIENT["独立微信小游戏：Cocos 2D"]
  CLIENT --> API["Go 游戏接口：认证、校验、结算"]
  API --> SIM["可解释农艺与经营模型"]
  API --> DB["MySQL：存档、批次、账本、动作"]
  ADMIN["现有 Vue 后台：规则、剧本、回放"] --> API
  CLIENT --> ASSET["版本化图片与音频资源"]
~~~

单人经营首版采用请求与响应，不需要持续 WebSocket 或帧同步。渲染帧率和服务器结算频率相互独立。

### 6.2 状态由服务器决定

客户端发送“给地块 3 灌溉一个方案”“采用中等疏果”“采收批次”等操作意图，不上传自算后的产量、品质、货币或库存作为正式结果。

正式请求携带 requestId、expectedVersion 和操作参数。建议事务顺序：

1. 校验登录身份与存档归属，锁定该农场记录。
2. 查找同一 requestId；已经执行的动作返回原结果，并提供最新存档版本信息。
3. 与尚未补算前的持久化版本比较 expectedVersion，拒绝客户端已知状态被其他操作更改的请求。
4. 依据服务器时间补算已结束的模拟日，确定当前动作生效日；大量积压时先完成同步再接收动作。
5. 根据补算后的物候、资源和库存验证动作。
6. 应用合法动作，将资源扣减、库存变化、账本、结果和新存档在同一事务内提交。

如果补算后动作窗口已经关闭，返回最新状态与具体原因，不产生动作费用。可将此次拒绝结果和补算状态一并提交，保证弱网重试稳定；规则需在接口契约中固定。

农场级行锁和数据库唯一约束负责并发控制，不能只靠单实例 Go 内存锁。MySQL 的锁定读用于保护事务中的读取和后续修改。[MySQL 8.4：Locking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

同一请求号更换参数必须拒绝。客户端仅接受不低于当前版本的快照，避免旧响应覆盖新状态。收获、销售、设施购买与奖励发放都使用相同的幂等原则。

### 6.3 离线推进

存档记录 lastSettledAt、模拟时间、季节、规则版本、模拟内核版本、天气剧本及服务器生成的随机种子。进入游戏、恢复前台和执行动作时补算。

在线与离线采用同一计算顺序。先按日步进，后续仅在等价性验证通过时优化为跨日或跨阶段计算。长时间离线由 game.sync 固定目标模拟日并按有界批次补算，继续从已提交的检查点推进；页面展示同步进度。

分批同步未完成时暂停动作提交，动作接口只返回“待完成同步”，不扣资源。同步结束获取最终 version 后，客户端再提交操作。常规动作事务内部的少量补算发生在 expectedVersion 校验后，不应因自身推进而产生版本冲突。

每季锁定规则版本、模拟内核版本和天气。规则更新默认从新季开始生效，防止调参突然改变正在进行的农场。按“服务器种子 + 季节 + 地块 + 模拟日 + 事件类型”确定同一事件的随机样本，保证分段同步和刷新不改变抽样结果；若改用连续随机流，必须持久化其状态并固定调用顺序。

补算过程不发实时外部请求。天气已预先保存，通知任务与结算分开，避免外部服务故障拖住数据库事务。

### 6.4 建议数据表与接口

以下名称为新增建议，并非已实现代码。

| 表 | 内容与必要约束 |
| --- | --- |
| game_farms | 所属业务用户、季节、模拟时钟、lastSettledAt、规则及内核版本、weatherId、seed、version；索引定位本人存档 |
| game_plots | 地块配置与农艺状态；少量地块首版可合并到 game_farms 的 checkpoint JSON，规模扩大后拆表 |
| game_actions | requestId、参数摘要、动作类型、执行时间、结果和版本；唯一约束 farmId + requestId |
| game_inventory_batches | 采收日期、初始品质、等级、保鲜方式、剩余重量与版本；销售不能超过可用量 |
| game_ledger | 收入、成本及资源变化，与来源动作关联；设置来源唯一约束 |
| game_rule_versions | 经过审核的不可变规则配置、来源、发布状态、校验结果及适用范围 |
| game_weather_scenarios | 按模拟日排序的天气过程、数据来源和授权信息 |
| game_identity_links | 业务用户与 AppID + OpenID 的关联，避免跨应用标识混用；关联双方设置必要的唯一约束 |

金额采用整数最小单位；重量等数值统一量纲和精度，明确取整位置。正式库存不从客户端缓存读取。

核心 action 可采用 game.bootstrap、game.sync、game.action、game.inventory.list、game.ledger.list、game.season.summary。农事、采收和销售作为 game.action 的受限类型处理。

后台 action 采用 admin.game.rule.*、admin.game.scenario.*、admin.game.simulate 和 admin.game.overview，并登记读取、编辑、审核发布等权限。扩展现有配置与审计时，增加游戏类型的白名单、验证和脱敏规则。

### 6.5 独立小游戏的身份衔接

小游戏新增自己的微信登录交换与受限会话。身份标识使用 AppID + OpenID，不假设两个应用得到相同 OpenID；服务端区分小游戏与原小程序登录来源及会话权限。

满足开放平台关联等条件时，可评估 UnionID 作为身份关联依据；也需要允许暂时拿不到 UnionID 的用户正常游玩。CloudBase 官方身份关联方案讨论了 UnionID 跨应用关联，但当前项目使用自建 Go 身份体系，不能直接套用其 SDK 来自动完成迁移。[CloudBase：Account Association](https://docs.cloudbase.net/en/authentication/auth/account-linking)

小程序进入小游戏时，可由服务端生成短期、一次性绑定凭证，限定目标 AppID 与用途；小游戏先完成自己的微信登录，再兑换凭证并明确确认关联。凭证只允许使用一次并记录结果；已有关联冲突时拒绝覆盖，不传长期 Bearer 令牌、session key 或支付凭据。

既有普通小程序数据继续使用原身份。新增映射层将游戏账号关联到现有业务账号，首版无需重写整个商城用户体系。

小游戏用户也可以直接从小游戏入口进入，因此登录与经营不依赖来自商城的跳转凭证；身份关联是跨应用进度或业务联动的附加步骤。初次关联时如双方已有游戏存档，不自动合并资产，采用明确的冲突处理流程。

账号注销和数据删除需同步扩展：现有代码主要按原小程序 OpenID 删除数据，而新表以业务用户及 farmId 关联，不能只加入原删除表清单。应根据身份映射删除游戏存档与关联数据、撤销小游戏会话；小游戏写入、绑定、补算和原账号注销共享同一业务账号锁与关闭状态，防止删除后重建存档。正式实现应验证来自两端的并发注销与操作。

微信官方跳转 API 定义包含小游戏目标和 extraData，但实际往返、参数接收、返回课堂或商城需要使用两个真实 AppID 验证；不能只在模拟器验收。[微信官方跳转接口定义](https://github.com/wechat-miniprogram/api-typings/blob/master/types/wx/lib.wx.api.d.ts)

新增小游戏的网络传输可以选择经过验证的云开发访问能力，或 HTTPS 访问同一 Go 服务；域名、鉴权入口、应用凭据和云环境权限应分别配置。

## 7. 运营与 AI 的使用位置

运营后台至少需要品种与阶段参数、天气剧本、设施与成本、品质分级、销售渠道、教学内容关联、规则发布与回放。

规则发布前自动检查：阶段可达、参数范围、单位一致、库存不为负、资源守恒、模拟结果无异常数值。发布记录绑定审核人和版本，支持回滚当前发布指针，同时保留旧季所使用的版本。

经营概览关注首季完成率、关键农事执行率、不同策略的产量与利润分布、常见失败原因、课堂点击与游戏后商城访问；当前账号数据和游戏数据删除逻辑同步扩展。

首版无需实时大模型参与生长与收益判定。原因解释可以直接由规则事件生成模板文案。后续 AI 适合在经过审核的课堂资料上回答问题，或帮助运营整理案例；正式扣款、产量和奖励仍由可复现规则决定。

## 8. 开发步骤、工期与成本

以下为工程量级估算，不是外包报价，也不是已完成的开发排期。假设两名开发人员，另有美术支持、种植专家审核及兼职产品测试；只覆盖上述有限首版，不包括公开上线审核等待、出版资质流程或大规模原创动画制作。

| 阶段 | 交付物 | 估计时间 |
| --- | --- | --- |
| 技术与农艺原型 | Cocos 一块地、阶段推进、灌溉和采收、结果解释；小游戏真机测试与双 AppID 跳转；账号资质核验 | 约 1–2 周；外部回复时间另计 |
| 种植经营闭环 | Go 模拟、操作事务、离线补算、分级库存、虚拟销售、存档 | 约 2–3 周 |
| 画面与后台 | 多地块、短动画、设施、规则发布、教程关联与复盘 | 约 2–3 周，可与上阶段部分并行 |
| 校准与验收 | 专家案例回放、弱网并发、资源性能、现有业务回归、小范围试玩 | 约 1–2 周 |

在上述人力和范围下，独立微信小游戏达到可内测首版约 6–10 周；存在原创美术、农艺资料不足或跨应用身份复杂度时应重新估算。一个人兼顾客户端、后端、美术和测试不能按同样日历时间承诺。

实施前先确认当前完整 Go 服务可编译、适用数据库迁移已执行，并完成真实 MySQL 基线联调。本次只读调研未执行这些检查，不将仓库历史验收报告中的编译问题视为当前已确认故障。

主要成本是游戏美术、农艺规则整理与反复校准、客户端实现和后台验证。云端成本由容器 CPU 与内存、数据库、静态资源流量和日志等组成；复用现有服务不等于没有增量成本。CloudBase 不同云托管环境的计量与套餐口径有所区别，需根据实际环境核算。[CloudBase 云托管计费说明](https://docs.cloudbase.net/run/faq/fee)

举例：1,000 日活、每人每日 30 次服务端同步或操作，约 30,000 请求/日；10,000 日活、每人每日 50 次，约 500,000 请求/日。后者平均约 5.8 请求/秒，但活动和登录高峰远高于平均。该算式只是容量规划输入，不能证明现有 20 连接池足够。

压测时同时模拟商城结算和游戏操作，测连接池等待、账号锁等待、补算耗时、事务冲突与错误率。若游戏影响交易体验，再拆游戏服务、独立连接池并设置资源配额；首版不必直接引入微服务、Redis 或消息队列。

## 9. 原型与正式实现的验收重点

本次调研未执行下面这些验收。它们是后续开发的交付标准建议。

| 验证对象 | 应证明的结果 |
| --- | --- |
| 农艺因果 | 正常管理、过载、缺水、供水突变、过度暴露等专家案例产生合理方向；条件变化能改变策略优劣 |
| 离线一致性 | 相同天气、动作和时间跨度，连续在线与分段离线补算得到等价结果，误差在预定范围内 |
| 幂等和并发 | 重复点击、超时重试、两设备同时收获/销售均不重复扣款、入库或记账 |
| 库存与经济 | 总收获重量、分级量、出售量、损耗和剩余量可核对；不出现负库存或重复成本 |
| 身份和数据删除 | 本人存档隔离、退出和注销生效；绑定票据过期及重复使用失败，两端并发注销不重建已删除数据 |
| 配置版本 | 已开季继续使用原规则，新季使用新规则；回放能定位来源与版本 |
| 真机和资源 | Android、iOS 和较低性能机型验证拖动、点击、隐藏恢复、弱网、内存与音频；持续游玩无资源增长异常 |
| 现有业务 | 首页、课堂、商城、登录与个人数据流程通过相关回归；游戏压力下商城响应符合原要求 |
| 发布条件 | 当前账号类目、资质、包体、网络配置及实际跨应用跳转完成验证 |

原型性能目标可先设为：限定约 24 个可见地块时，短动画达到约 30 帧/秒；正常网络下进入模块到可操作约 3 秒以内；常规动作服务端处理 P95 约 500 毫秒以内。上述为可调整目标，不是平台保证或当前实测数据，须记录设备、网络、冷热启动和补算长度。

## 10. 实施前最值得确定的四项

1. 游戏对应的真实种植地区、主栽品种、棚架与露地/避雨/设施方式。
2. 能参与规则审核的种植人员，以及可提供的生产记录与课堂材料。
3. 玩家主要是消费者还是种植学习者；决定教学深度、难度和每次操作时长。
4. 新小游戏 AppID、主体、具体游戏类别与发布资质，以及两个应用的开放平台关联条件。

建议按已确定的独立微信小游戏路线，先完成“一个真实品种、一个成园地块、一季经营”的可试玩原型，验证同样天气下，不同管理会产生可解释的商品率和利润差异，再扩展地图与品种。
