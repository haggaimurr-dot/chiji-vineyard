# 正式退款验收

本地自动检查验证代码和模拟流程，不代表真实资金退款已验收。当前小程序默认演示模式，真实商户、验收环境、回调和支付账户到账证据尚未提供，以下实单项目保持待验收。

## 页面与接口

- 订单详情可进入「查看退款进度」。售后页保留申请表、部分金额和举证功能，展示各次申请的金额、单号、申请时间、状态更新时间、审核进度与拒绝原因。
- `refund.list` 接收 `orderId`，只允许订单本人查询；传 `refresh: true` 时查询最新处理中或异常的微信退款。查询失败显示错误并保留页面已有记录，不制造成功状态。
- 后台退款列表显示中文状态与拒绝原因，拒绝原因必填。处理中支持 `admin.refund.sync` 查询微信，以及 `admin.refund.approve` 按原退款单号重试提交；异常须在商户平台核实，禁止直接重新创建退款单。
- 审批先在事务中锁定退款与订单并保存处理中状态，再请求微信。网络失败保留待确认状态；同一退款单重试使用原 `out_refund_no`。
- 成功、异常、关闭回调均验签、解密并核对退款单号、订单号、商户和标价退款金额 `amount.refund`。用户支付优惠可能使 `payer_refund` 不同，不能将其作为标价金额比较。只在微信确认成功后更新累计退款；重复成功及迟到处理中通知不重复恢复库存或覆盖已成功状态。

接口字段与微信状态参考：[微信支付查询退款](https://pay.wechatpay.cn/doc/v3/merchant/4012587973)。

## 验收环境准备

1. 使用独立验收数据库、云托管服务和管理员账号；按部署手册执行当前建表及相关迁移。
2. 配置真实小程序与绑定商户，设置 `WECHAT_MCH_ID`、`WECHAT_MCH_SERIAL_NO`、商户私钥、微信支付公钥及 ID、API v3 密钥。`WECHAT_REFUND_NOTIFY_URL` 必须是微信可访问的 HTTPS `/wechat-pay-notify`。
3. 小程序设 `demoMode: false` 并填写真实云环境与服务名；后台关闭 mock。密钥留在后端环境中，验收记录不得包含密钥、令牌或完整个人资料。
4. 先创建并支付一笔低额订单。记录订单号、支付交易号、支付金额与支付前后 SKU 库存/销量，确认用户与商户两侧支付成功。

## 实单检查（均待验收）

| 用例 | 操作 | 通过标准 |
| --- | --- | --- |
| 提交与进度 | 用户提交，退出页面再进入 | 显示真实单号、金额、时间及待审核；重复点击不能新增进行中申请 |
| 审核拒绝 | 空白原因提交，再填写真实拒绝原因 | 空白被拒绝；两端显示同一原因，拒绝记录保留；符合条件可再次申请 |
| 原路退款 | 审批另一笔已支付申请 | 先显示处理中，微信成功后显示退款成功；用户账户与商户退款单一致 |
| 库存与销量 | 完成未发货整单退款 | 库存与销量按订单数量恢复一次；已发货退款不增加可售库存 |
| 部分退款 | 先退部分，再退剩余额 | 每笔记录独立，累计金额不超支付额；部分退款不按金额推算退货数量 |
| 并发审核 | 同时同意、拒绝、发货或再次申请 | 状态互斥，不出现已拒绝仍扣款、退款中发货或重复资金退款 |
| 提交断网 | 在微信已受理、本地尚未得到结果时中断连接 | 保留待确认；主动查单能恢复；原单重试不产生第二笔退款 |
| 回调缺失 | 验收环境暂停接收退款回调，再主动查询 | 主动查询成功可补齐订单、累计金额与库存；恢复回调后不重复结算 |
| 重复/乱序 | 受控测试工具发送有效重复回调及迟到状态 | 库存、销量和累计金额保持一次结算，已成功状态不降级；不能只重放过期报文 |
| 异常/关闭 | 通过官方可用的测试条件或受控模拟响应测试 | 两端显示异常待处理，不显示到账、不恢复库存、不放开重复申请；实单异常以商户平台结果核实 |
| 验签与金额 | 受控测试中改变签名、时间戳、商户、订单、单号或金额 | 拒绝无效通知，不改订单、退款及库存；合法支付优惠差额不误拒绝 |
| 用户权限 | 用户 B 查询用户 A 的退款与举证 | 返回不存在或拒绝；不泄露原因、图片及金额 |
| 查询失败 | 查询超时或供应商报错 | 页面显示重试提示并保留已有记录；后台显示具体错误，不显示虚假成功 |

第三方真实异常难以主动构造时，必须分别记录「受控模拟通过」与「实单未执行」，不得合并为实单通过。

## 本地验证

执行 `npm run check`、`npm run mini:build`、`npm run test:flows`，以及 backend 目录的 `go test ./...`、`go vet ./...`。退款进度自动检查覆盖拒绝原因、状态展示、查询失败恢复、支付优惠金额核对、异常到成功、重复与乱序结果，以及库存事务回滚。真实 MySQL 并发、微信开发者工具布局与资金到账仍按上表验收。

## 原路退款到账专项验收（2026-10-07）

后台退款列表及小程序退款进度增加微信退款单号 `providerRefundId`，用于与商户平台记录逐笔核对。该字段来自已验签查单或回调的持久化结果；历史无单号记录留空。页面退款成功表示微信已确认成功，正式到账验收还须核对原支付账户凭证。

每个退款验收批次填写 [退款到账证据模板](REFUND_RECEIPT_ACCEPTANCE.csv)，当前无真实商户交易与用户到账凭证，状态保持「待执行」。模板不能用演示数据标记通过。

1. 按前文准备独立验收环境，记录版本、验收人及低额订单的真实支付流水。由支付账户持有人查看原支付渠道的退款明细，脱敏保留支付账户标识，不能用后台状态截图代替。
2. 提交并审批退款，记录订单号、本系统退款单号、微信退款单号。处理中与微信异常时不得填写到账时间或通过状态；到账等待超出商户平台显示的预计时间时，关联售后工单跟进并主动查单。
3. 微信成功后核对原支付路径、实际账户明细到账时间和到账金额。将标价退款金额 `amount.refund` 与退款申请核对，将实际到账与商户明细的 `payer_refund` 核对。存在支付优惠时分别记录优惠差额，不能要求实际到账必然等于标价退款金额。
4. 至少对整单退款、部分退款后剩余退款逐笔取证。对重复回调、回调丢失查单补齐及原退款单重试，核对资金流水只有一笔，累计退款和库存销量无重复结算。控制模拟只证明代码流程，真实资金去重须用真实流水证明。
5. 验收人核对用户账户凭证、商户退款明细、两端页面及脱敏数据库记录，填写证据路径。证据缺失、金额不符、路径不符或流水重复均不可标记通过。金额使用分，到账时间记录带时区的原始时间，并换算为北京时间。

必须完成前文实单表的必需用例以及本专项整单/部分金额到账检查，才能签署正式验收完成。尚未执行的实单不由本地测试替代。
