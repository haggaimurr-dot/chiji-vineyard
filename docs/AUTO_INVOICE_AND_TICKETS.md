# 售后工单与自动开票

售后工单入口在小程序订单详情及后台「订单与售后」。用户提交品质、物流、发票或其他问题；后台可从订单进入工单列表，也可从退款申请创建关联该退款的工单。一个订单同时仅允许一个未关闭工单，重复提交提示到原工单补充说明。工单支持图片附件、处理期限、未读回复提醒、负责人（有效管理员用户名）、公开回复和处理记录，状态为待处理 → 处理中 → 已解决 → 已关闭，也可直接从待处理标为已解决；解决和关闭必须填写结果。用户在已解决工单补充说明会恢复为处理中。已关闭工单不可修改，可以重新提交。

工单不执行退款，退款金额及微信到账状态仍在原退款流程中处理。小程序只读取本人订单工单；后台查看使用 `refund.read`，创建、分配及回复使用 `refund.approve`。版本校验防止旧页面覆盖新处理结果；后台写入及操作日志在同一事务中提交。列表每页50条。

已有数据库执行 `backend/migrations/20261006_after_sales.sql`。新数据库执行完整 `backend/schema.sql`。自动开票沿用 `invoice_requests` 的 JSON 字段及 `invoice_files`，不需要新增开票表。

## 自动开票启用

配置 `INVOICE_GATEWAY_URL`（HTTPS）及 `INVOICE_GATEWAY_TOKEN`，后台待开票订单可点击「自动开票」。配置 `AUTO_INVOICE_ENABLED=true` 后，服务每10秒扫描待申请发票，包含启用前已存在的待开票申请。关闭该开关只关闭定时扫描，已配置网关时仍可后台手动触发。默认关闭，服务未配置时继续使用上传真实发票流程。

此项目定义了通用开票网关协议，没有内置特定税务服务商 SDK。生产使用需由商家的真实开票服务实现下述网关适配及联调，不能把普通 PDF 或演示 PDF 当作合法发票。未配置网关不会生成发票号码或 PDF。供应商凭证仅配置在服务端。

POST 网关地址，`Authorization: Bearer <token>`，`Idempotency-Key: <requestId>`。JSON 请求包含 `requestId`、`orderId`、`orderNo`、`kind`、`title`、`taxId`、`amount`（分）及 `items`（订单项目）。网关按订单商品开具真实电子发票，返回 HTTP 200：

```json
{"status":"ISSUED","requestId":"原请求编号","number":"真实发票号码","fileName":"invoice.pdf","fileData":"PDF 的 Base64","amount":12345,"title":"申请抬头","taxId":"申请税号（个人为空）"}
```

网关必须持久化请求编号、保证同编号重复请求不会重复开票，并返回原发票和 PDF；查询既有请求结果也使用相同 POST 和编号。无法立即返回已开票结果时可返回 `PENDING`，应用将保留待核实状态。明确拒绝且保证未开票时返回 `{"status":"REJECTED","requestId":"原请求编号"}`。返回抬头、税号、金额及请求编号须完全一致；PDF 不超过3MB。

请求超时、服务错误、格式错误、资料不一致或无效 PDF 均标记「结果待核实」，不自动重试。后台「按原请求核查开票」始终复用原编号。超过一分钟仍处于处理中会转为待核实。明确失败或退款暂停后可后台重试。服务在处理中、待核实期间禁止人工开票、退回申请及新申请/批准退款，避免并发开票与退款。若进程在存储结果前中断，恢复后使用相同编号取回网关已开具结果。

成功后私有保存 PDF，并调用现有 SMTP 邮件发送流程；邮件失败不会撤销已开具发票，可以单独重试。退款发生在开票完成后需人工处理红冲等税务后续流程，当前功能不自动红冲。通过 `internal.autoInvoices` 可由带 `X-Job-Secret` 的内部任务触发一次扫描。

演示环境后台自动开票生成标有 `DEMO ONLY - NOT A TAX INVOICE` 的示例 PDF，模拟邮件结果，不调用真实服务。后台工单和小程序工单演示数据独立，不能跨端同步；小程序工单本地保存。

## 验证

`go test ./...`（backend）覆盖工单归属、退款关联、重复提交、版本冲突、状态变更、负责人校验、审计失败回滚，以及开票请求鉴权、同编号重试、超时/错误、资料与 PDF 校验。`npm run test:after-sales` 验证两端演示流程；`npm run test:after-sales-ui` 验证后台负责人分配、回复、解决、关闭、新建、自动开票下载及1024像素布局；`npm run test:invoices`、`npm run test:refunds` 验证已有退款、发票下载及邮件流程；`npm run check` 验证类型与后台构建。真实税务网关、MySQL 并发、SMTP 实际收信及微信页面运行仍需在对应环境验收。

## 附件、处理期限与回复提醒（2026-10-07）

小程序和后台均可在创建、补充和回复工单时添加图片附件，每次最多3张JPEG/PNG、原始文件合计512KB，必须填写文字说明。服务端校验Base64、真实图片格式、完整图片及尺寸，并限制工单累计附件约6MB。附件随消息保存在工单私有JSON中，不进入公开媒体库；仅本人订单用户及具备 `refund.read` 的后台账号可读取。后台可预览、下载，小程序可点击预览；选择失败保留草稿，上传期间禁用提交。当前附件类型为图片，PDF、视频及其他文件未开放。

新工单默认48小时处理期限。后台可将期限调整为未来30天内的时间；用户不能改期限。历史工单没有该字段时按创建时间加48小时显示。已解决、已关闭停止超时提醒；用户补充已解决工单会恢复处理中，并重新给予48小时期限。期限修改随工单版本和操作审计提交，不自动关闭、退款或发送处理结果。

两端列表显示未读对方消息数量与处理超时提醒，在页面可见且没有草稿操作时每30秒刷新。点击工单详情才确认已显示消息为已读，单纯刷新列表不会清除提醒。`ticket.read` / `admin.ticket.read` 接收 `id`、`version`、`readThrough`（已显示消息数量）；确认已读不递增工单版本，旧版本确认会被拒绝，防止并发新回复被吞掉。后台已读为客服团队共享；已读接口只需要读取权限且不能修改负责人、处理期限或状态。写回复、改期限仍需要 `refund.approve`。

提醒目前在工单页面内显示，小程序退到后台后停止轮询，返回页面重新查询。没有配置微信订阅消息模板，也不发送短信或系统推送。验收时分别检查用户补充→后台未读、后台回复→用户未读、打开详情清除提醒、仅刷新保留提醒，以及超时、解决、重开和草稿期间轮询暂停。

新增字段全部存储于已有 `after_sales_tickets.payload`，无新增数据库迁移。正式环境仍须先具备原工单表迁移。

本次本地验证：`npm run check`、`npm run test:after-sales`、`npm run test:after-sales-ui`、`npm run test:refunds`、`go test -run 'Test(AfterSales|Refund)' -count=1 ./...` 及 `go vet ./...` 通过。专项覆盖图片内容伪造/超量、归属与只读权限、处理期限越权/范围、已读版本冲突、未读提醒、已解决工单重开及两端附件流程。后端全量 `go test ./...` 仍有降价和补货通知相关测试失败，未作为本次专项通过结果。正式MySQL、微信小程序真实预览和资金到账尚未执行。
